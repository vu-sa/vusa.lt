# Changelog

## Release entries: main changes, every role, then other fixes
Each `## vX.Y — Title (YYYY-MM-DD) {#vX-Y}` entry stays h2 (config.ts builds changelog-meta.json from it) and contains, in order:
- a 2–4 sentence intro (a major adds the `[Atsisiųsti PDF](/vusa-lt-vN-atnaujinimai.pdf)` line), optionally one overview screenshot;
- the main features as numbered `### 1. …` headings, most important first, each paragraphs + screenshot + guide link;
- ALWAYS these four role `###` headings in order: Studentų atstovams, Studentų atstovų koordinatoriams, Komunikacijos koordinatoriams, Išteklių administratoriams. Inside a role, a change with a screenshot gets a `####` heading and prose (no emoji, no bullet); changes without one follow as ⭐/✨/🔧 bullets below them. A role with nothing new says „Šioje versijoje naujų pakeitimų nėra.“ or links the main feature that covers it;
- `### Kiti pakeitimai ir pataisymai {#vX-Y-kiti}`: ⭐/✨/🔧 bullets.
Before listing a change under a role, check that role can actually do it (guide's Kas ką gali, Role*Seeder.php). EN mirrors the same headings and anchors without screenshots.

## Changelog screenshots: reuse guide frames, annotate with highlights
Reuse an existing guide frame when it already shows the change. When the reader needs to know where to look, capture an annotated variant `vN-<topic>` right after the clean frame in the same browser test: `docsScreenshot($page, 'vN-topic', highlights: ['[data-slot=…]', …])` draws numbered red boxes. Explain the numbers only in that image's `caption`, in numeric order („(1) …, (2) …“); the body text never cites them. Overview frames (an entry's opening screenshots) stay unannotated. Highlights don't scroll and throw when a selector is off screen, so position the page first. A genuinely new frame is captured clean and also embedded in its guide page; annotated `vN-*` frames stay changelog-only. `node docs/pdf/build-release.ts` builds the PDF from the newest vN.md.

## Freeze a major's release notes when the next one starts
Screenshots are regenerated by CI on every deploy, so old notes would silently show the newer UI. When vN+1.md is created: commit vN's frames to `docs/public/releases/vN/` and its built PDF, point vN.md's images and PDF link at those files, and drop the `vN-*` docsScreenshot calls from the browser tests.

## Changelog tone: plain and measured
Write like a short release note from a colleague, not an advert or a chat: neutral statements of what changed and what it lets the reader do ("Kiekvienai pranešimų rūšiai gali pasirinkti, kaip ją gauti"). Use tu where it is natural, but no colloquialisms or pep ("po ranka", "Reikia ramybės –", "Nebereikia laukti", "nepradingsta"), and no imperatives as headings ("Atsakyk…"); headings name the change ("Atsakymas į koordinatoriaus užklausą"). Each fact appears once — don't repeat a caption in the text.
