# Changelog

## Entries are dated, never numbered
Entries carry the release date and no number: minor numbers meant nothing to readers and every parallel branch claimed the same next one. Several entries may share a date — add yours on top, no renumbering, no explicit anchor. Majors (`vN.md`) stay as eras: only the entry that launched one carries `{#vN}`, and its sections may use `{#vN-topic}` anchors. Guide text says „Iki 2026-10-26“ or „Nuo v3“, never a minor number.

## Release entries: scale the structure to the change
Each `## YYYY-MM-DD — Title` entry stays h2 (`changelogEntryPattern` in `docs/.vitepress/changelogEntries.ts` reads it for changelog-meta.json, ChangelogNote links and the PDF) and contains, in order:
- no meta intro about the document itself; a major opens with the `[Atsisiųsti PDF](/vusa-lt-vN-atnaujinimai.pdf)` line and the one-sentence link legend (*Gide* vs *Mano VU SA* ↗);
- main features, most important first (shape below). Number `### 1. …` headings only when there are several substantial features; a single feature uses an unnumbered heading;
- optional role `###` sections only for substantial changes specific to that role. When included, use this order: Studentų atstovams, Studentų atstovų koordinatoriams, Komunikacijos koordinatoriams, Išteklių administratoriams. Omit empty sections, “nothing new” notices and sections that merely repeat a shared feature. Inside a role, a change with a screenshot gets a `####` heading; smaller changes use ⭐/✨/🔧 bullets;
- `### Kiti pakeitimai ir pataisymai` when needed: one concise ⭐/✨/🔧 bullet per change type or affected area (e.g. news, contacts, resources), grouping closely related fixes.
Small releases can use a short feature description followed by these bullets, with no role sections; a fixes-only release needs only bullets. State each change once, where it is easiest to find.
Before listing a change under a role, check that role can actually do it (guide's Kas ką gali, Role*Seeder.php). EN mirrors the same headings and anchors without screenshots.

## Feature section shape: lead, screenshot, details, links
- First paragraph: one or two sentences naming what is new for the reader („Rezervacija nuo šiol pildoma kaip krepšelis“). No overview screenshots at the top of the entry — each frame goes right after the paragraph it shows.
- One idea per paragraph; details and the one notable exception come after the screenshot.
- Edge cases, internal rules and how-it-is-computed (trash behaviour, re-validation, completion rules shared by filters) stay in the guide, not the changelog.
- Close with one links line: `Gide: [Pranešimai](/pagrindai/pranesimai), [varpelis](/mano/pranesimai#kaip-tai-veikia) · Mano VU SA: [Pranešimų nustatymai](app:/mano/profile/notifications)`. Bullets end the same way. EN uses `Guide:` / `My VU SR:`. Don't use a markdown list for links — it merges with the ⭐/✨/🔧 bullets that follow.
- Link text names the page or UI label, never „Plačiau“. `app:/mano/…` opens the platform in a new tab with ↗ (web and PDF); a plain `/mano/…` link is the guide's Mano section. Take app paths from `route:list`; no `{id}` routes.
- Bullet titles name the change in the reader's words, quoting UI labels in „…“ („Darbotvarkės klausimai „Nerodoma““), not implementation terms.

## Changelog screenshots: reuse guide frames, annotate with highlights
Reuse an existing guide frame when it already shows the change. When the reader needs to know where to look, capture an annotated variant `vN-<topic>` right after the clean frame in the same browser test: `docsScreenshot($page, 'vN-topic', highlights: ['[data-slot=…]', …])` draws numbered red boxes. Explain the numbers only in that image's `caption`, in numeric order („(1) …, (2) …“); the body text never cites them. Overview frames (e.g. the home page) stay unannotated. Highlights don't scroll and throw when a selector is off screen, so position the page first. A genuinely new frame is captured clean and also embedded in its guide page; annotated `vN-*` frames stay changelog-only. `node docs/pdf/build-release.ts` builds the PDF from the newest vN.md's launch entry only (the one marked `{#vN}`); later entries sit above it and stay web-only, so the PDF link and link legend stay in the launch entry.

## Freeze a major's release notes when the next one starts
Screenshots are regenerated by CI on every deploy, so old notes would silently show the newer UI. When vN+1.md is created: commit vN's frames to `docs/public/releases/vN/` and its built PDF, point vN.md's images and PDF link at those files, and drop the `vN-*` docsScreenshot calls from the browser tests.

## Changelog tone: plain and measured
Write for everyday platform users, including administrators without technical knowledge. Say what they can do, what they will see, or what now works correctly. Keep bullets to one or two short sentences plus relevant links. Leave image formats, pixel sizes, storage, migrations and other implementation details in the guide unless the reader needs them to act. For example, say “Nuotraukos svetainėje ryškesnės”, not “Nuotraukos saugomos WebP formatu iki 3840 px”.

Write like a short release note from a colleague, not an advert: neutral statements of what changed. Describe, don't instruct — the guide gives steps, so prefer „galima“, „rodoma“, „nuo šiol“ over imperatives („pasirink“, „pradėk“); keep tu only where it reads naturally („tavo krepšelis“). No pep or colloquial filler („po ranka“, „Nebereikia laukti“, „nepradingsta“); one light aside in a whole release is fine („kaip el. parduotuvėje 😅“). Give a concrete example where a category is abstract („pvz., narių registracijos“). Don't overclaim: if only some actions moved, say „dalis“, not „visa“. Headings name the change („Atsakymas į koordinatoriaus užklausą“). Each fact appears once — don't repeat a caption in the text. Don't describe fixes to the unreleased candidate itself („vėl sutampa“) — the reader never saw the broken state.
